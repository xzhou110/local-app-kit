# Decisions

One dated entry per non-obvious choice: what was decided, why, and what it replaces (principle 9 of `D:/Meaningful/AI/agent-skills/rules/engineering-principles.md`). Newest first. A deviation from the standard is an entry here, never silent.

- 2026-10-22 — **First version is the server runtime only.** Ten modules lifted from the four apps (`README.md` lists them). Not in: the browser client (`createFileEditor`, the single shared `EventSource`), which only career-center has in that shape; the Electron shell commons (three shells with three window behaviours); the launchers. Each comes when a second app needs it in the same shape, as a new entry here.

- 2026-10-22 — **Behaviours unified where the copies disagreed**, each toward the stricter or safer rule: dot-segment and double-encoded targets answer 400 before URL normalisation (ai-usage-tracker's rule; career-center answered 404); `writeAtomic` without `ifMatch` only creates (career-center's rule, safe by default); non-GET methods on static paths answer 405 (creator-advisors' rule); the Origin check accepts the three loopback forms on the bound port (a superset of ai-usage-tracker's exact-Host rule, still loopback only). The parity suite pins each one; `README.md` Behaviour Notes tells a migrating app what changes.

- 2026-10-22 — **Failures are values.** Every module answers an expected condition with `{ ok: false, reason, status }` (a conflict, a locked target, a held lock, a bad target, an oversized body, a taken port) and throws only for programmer errors; the app maps results to its own error envelope and wording. ai-usage-tracker's lock threw its `AppError`; the kit returns the same cases as results so no app's error type leaks into the kit.

- 2026-10-22 — **The kit is adapter-layer code: no engine folder.** Its subject is files, sockets and processes, so the standard's pure-engine layer does not apply; the audit's engine row is N/A by this entry. The boundary lint is still loaded (the size rule applies; the engine globs match nothing). Layout: `src/<module>.ts` with `<module>.test.ts` beside it, `parity/` for the consumer suite, `dist/` the build.

- 2026-10-22 — **Tests run with `node --test` on the `.ts` files directly.** Node 24 strips types outside `node_modules`, so the kit needs no test runner and has zero runtime dependencies (principle 10). The consumers keep their own runners (vitest, node:test); the parity suite here is the acceptance they share. `src/test-support.ts` holds the helpers and stays out of the package.

- 2026-10-22 — **TypeScript 6 for the kit's own toolchain.** The sibling apps type-check with TypeScript 7 (the native compiler), but `typescript-eslint` 8.72 supports TypeScript below 6.1, so the kit builds and lints with 6.0.x. The emitted `.d.ts` files are plain declarations the TypeScript 7 consumers read. Move to 7 when `typescript-eslint` supports it.

- 2026-10-22 — **`dist/` is committed and gated.** Node refuses to strip types for files under `node_modules` (`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`, verified on this machine on 2026-10-22), so a package installed from git must ship JavaScript. `npm run check` rebuilds and `scripts/check-dist.mjs` fails when the committed `dist/` differs, so every tag's `dist/` is what its `src/` says. A `prepare` script that builds on every consumer install was considered and set aside: it would download TypeScript and run it inside each app's install, one more thing to fail behind this machine's TLS inspection; it stays available if committed output ever becomes a burden.

- 2026-10-22 — **A shared package consumed as a git dependency pinned to a tag, in a public repository (owner's choice, option A of the plan).** The local-app runtime was rewritten in four apps; principle 10 says the third consumer earns a shared package. A pinned tag (`git+https://github.com/xzhou110/local-app-kit.git#v0.1.0`) keeps releases uncoupled: a kit change reaches an app only when that app bumps and passes its own check. Public, because the kit holds runtime code and synthetic fixtures only, so installs and the consumers' GitHub Actions need no token and the kit's own gate runs on free minutes. Set aside: a vendored copy per app with a parity test (no install step, but four copies again and the standard moves past vendoring at the third consumer); the npm registry (tokens and a public semver commitment for an audience of one; a private package costs money); GitHub Packages (a token even for public installs); a monorepo or `file:` links (one repository per project is the workspace convention; a `file:` link breaks a fresh clone and CI); a git submodule (the standard forbids it). The plan the owner approved is in the side-session notes of 2026-10-22 and summarised in `PROJECT.md`.

- 2026-10-22 — **License: UNLICENSED in a public repository.** The code is published for installation convenience, not as an open-source offer; `package.json` says `UNLICENSED` so nobody mistakes it for one. The owner can choose a license later; that choice is theirs, not an assistant's.
